# 后台管理与 MySQL 开发方案

状态：后台页面、登录鉴权、供应商管理、聊天记录持久化和查询已实现，并通过离线测试；真实 MySQL、QQ 与模型联调待完成。当前启动步骤以 README 为准，以下保留设计与验收约定。

## 目标与技术方案

在现有 Python + LangChain + FastAPI 项目中增加后台，查看聊天记录并管理模型供应商。默认继续使用 DeepSeek，保留后续切换兼容接口供应商的能力。

- 页面：原生 HTML / CSS / JavaScript，由 FastAPI 提供静态资源，不额外引入前端构建工程。
- 后端：沿用 FastAPI，计划使用 `/admin` 页面与 `/api/admin` 接口。
- 数据访问：计划使用 SQLAlchemy 2 + PyMySQL；同步数据库操作放入线程池，避免阻塞异步消息处理。
- 数据库：复用用户已在 Docker 中启动的 MySQL；用户自行创建项目库，执行仓库提供的 DDL，库名以实际配置为准。
- 保持单进程部署；暂不增加 Redis、消息队列或多用户权限系统。

## 第一阶段功能

### 管理员登录

- 单管理员登录和退出，后台页面与数据接口均需鉴权。
- 管理员账号和密码哈希从本地环境配置读取，无默认公开密码；提供生成密码哈希的本地命令。
- 使用有过期时间的登录会话和 HttpOnly Cookie；配置 SameSite，HTTPS 部署启用 Secure，写操作校验 CSRF。
- 登录失败提供通用提示并限制尝试频率，不暴露配置或凭证。
- 后台可在尚未填写 QQ 凭证或尚未启用模型供应商时启动，页面明确提示缺少配置；聊天入口按实际配置检查可用性。

### 聊天记录

- 列表展示时间、来源、群标识、用户标识、问题、回复、模型和处理状态。
- 支持按时间范围、来源、群、用户和状态筛选，并进行分页查询。
- 详情展示完整问题、回复和经过脱敏的失败原因。
- 持久化收到的消息及处理状态，区分待处理、已回复、模型失败、发送失败和过期等结果。发送超时标记送达状态未知，不记录为已成功。
- 同一 QQ 消息重复推送不能生成重复记录；保留消息 ID 作为幂等依据。
- 同时记录本地命令行聊天，使用独立来源标识，避免与 QQ 会话混淆。
- `/reset` 清空当前上下文，但不删除后台历史记录。第一阶段不提供批量删除和导出。

记录持久化用于后台查询；重启后自动恢复模型上下文和未完成任务属于后续能力，本阶段不能据此声称已支持。

### 供应商、模型与密钥

- 新增和编辑供应商名称、接口类型、Base URL、模型名称和 API Key。
- 第一阶段支持 DeepSeek 和兼容 Chat Completions 的接口；不承诺支持所有供应商的专有协议。
- 支持启用、停用和设置默认供应商；不能停用仍为默认的供应商，应先切换默认项。
- 配置保存并启用后，从下一次模型请求生效，正在处理的请求继续使用开始时的配置。
- 密钥写入时加密，列表和详情只显示掩码及是否已配置；编辑时密钥留空表示保留原值，不把掩码当成新密钥提交。
- 加密主密钥仅保存在本地 `.env`，不与密文共同存入数据库。主密钥丢失将无法解密，需妥善备份。
- Base URL 限定 HTTPS，拒绝含用户名、密码或密钥查询参数的地址。仅管理员可修改模型请求目标。
- 后台设置的默认供应商优先；尚未配置默认供应商时可回退到现有 DeepSeek 环境配置。若默认供应商无效，明确报错，不静默切换。
- 保存配置不触发付费请求；如提供连接测试，必须由管理员明确点击，并说明会调用模型 API。

## 数据库设计草案

初始 DDL 已提供：[../sql/001_init.sql](../sql/001_init.sql)，要求 MySQL 8.0.16+。字段、约束及索引以该文件为准；尚未在用户实例中执行验证。

| 表 | 用途与主要字段 |
| --- | --- |
| `model_providers` | 名称、接口类型、服务地址、模型名称、加密密钥、启用状态、创建与更新时间 |
| `app_settings` | 单行运行配置，保存默认供应商 ID，避免同时存在多个默认供应商 |
| `conversations` | 来源、群标识、用户标识、创建与最近活动时间；按来源与会话身份建立唯一约束 |
| `chat_records` | 会话 ID、外部消息 ID、问题、回复、状态、脱敏错误、供应商及模型快照、接收与完成时间 |

- 使用 InnoDB 和 utf8mb4，确保中文及 emoji 可保存；时间统一按 UTC 存储，页面按用户时区显示。
- QQ 记录按来源、群标识和外部消息 ID 建立唯一约束；本地消息使用生成的唯一 ID。
- 为接收时间和会话查询建立索引，接口限制分页大小。
- 保留供应商名称与模型快照，使后续配置修改不改变历史记录的含义。
- 用户负责创建项目库，项目提供可重复执行的建表脚本，不在普通启动流程中删改已有数据。后续结构变化使用版本化迁移，`IF NOT EXISTS` 不负责升级结构。
- 数据库不可用时明确提示，不能在后台显示保存成功；QQ 入队确认前应完成接收记录落库，失败返回可重试错误，避免伪装成可靠持久化。

## 连接现有 Docker MySQL

不创建新容器，不修改现有容器数据卷，不重置已有密码。实现前需要确认：MySQL 版本、主机、映射端口、项目库名、数据库账号及相应建库/建表权限。

应用在 Windows 宿主机运行时，通常连接 `127.0.0.1` 和容器映射到宿主机的端口；应用也运行在容器内时，需要使用同一 Docker 网络中的 MySQL 服务名和容器端口，不能将应用容器的 `localhost` 当成 MySQL。

以下配置已实现并加入 `.env.example`；本地 `.env` 已生成，数据库账号和密码待填写。另有 `ADMIN_ENABLED` 控制后台及持久化开关，`ADMIN_COOKIE_SECURE` 控制 HTTPS Cookie：

| 配置 | 说明 |
| --- | --- |
| `MYSQL_HOST` / `MYSQL_PORT` | 已有 MySQL 的可访问地址及端口，不预设实际映射值 |
| `MYSQL_DATABASE` | 项目库名，建议 `qbot` |
| `MYSQL_USER` / `MYSQL_PASSWORD` | 数据库账号及密码，密码只填写到本地 `.env` |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD_HASH` | 后台管理员账号与密码哈希 |
| `ADMIN_SESSION_SECRET` | 后台会话签名密钥 |
| `PROVIDER_ENCRYPTION_KEY` | 供应商 API Key 的加密主密钥，与会话密钥分开 |

数据库运行账号仅需项目库内的必要权限。若该账号无建库权限，由有权限的账号先建项目库，再使用运行账号连接。

## 实施顺序与验收

1. 用户创建项目库并执行 `sql/001_init.sql`，再确认应用连接配置，验证建表结果和重复初始化行为。
2. 接入聊天记录持久化，验证隔离、失败状态和消息幂等。
3. 实现供应商管理及模型配置加载，验证加密、脱敏和切换生效。
4. 实现管理员登录、记录查询页面和供应商表单，包含加载、空数据、保存成功及失败状态。
5. 运行相关后端检查与函数式测试，模型默认使用模拟响应；按项目约定不打开浏览器验证前端。
6. 更新 README 的启动步骤、实际配置名与验证结果；实际连接和建表成功后才标注数据库初始化完成。

当前后台代码已实现，但尚未连接用户的 MySQL 或执行 DDL。现有无数据库启动方式仍可通过 `ADMIN_ENABLED=false` 使用。

DDL 中的 OpenID、来源和外部消息 ID 使用 ASCII 且区分大小写，避免标识比较与唯一索引失真；问题、回复和名称使用 utf8mb4。聊天记录通过复合外键校验来源与群标识是否属于对应会话。停用默认供应商、状态流转、URL 校验和密钥加密已由应用实现；DDL 本身只负责数据库约束。
