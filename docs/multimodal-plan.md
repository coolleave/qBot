# QQ 多模态对话与自动语音回复方案

状态：规划，未实现、未联调。日期：2026-10-25。

本文以用户提供的消息类型处理表为设计参考。截图中的模型名称作为候选配置，不代表已核验其账号可用性、地域、价格、接口协议或能力范围；实现前须查阅对应官方文档并核对 QQ 实际事件样本。

## 1. 目标与范围

同时支持 QQ 私聊和群聊中的图片理解、短语音转写、文字回复、自动语音回复及表情包理解。群聊沿用平台可收到的 @机器人事件，不扩展为监听整个群的所有消息。

本次仅形成文档，不修改业务代码、数据库、依赖和运行服务，不发起模型调用或 QQ 消息发送。

第一版包括：

- 照片、截图、静态表情包的内容理解与对话回复。
- GIF 动态表情包抽帧后理解，保留帧的先后顺序。
- 短语音识别为文字，再结合上下文回复。
- 普通文字和 Unicode Emoji 正常参与对话。
- QQ 内置表情在事件提供可识别 ID 时映射为名称。
- 按机器人和私聊／群聊场景配置文字或自动语音回复。
- 后台配置、识别结果、发送结果、错误原因和费用用量信息展示。

不包含视频理解、实时语音通话、自动生成表情包、声音复刻和声音设计。定时任务和后台手动发送继续使用各自流程，不因开启自动语音回复而改变发送形式。

## 2. 消息类型与模型分工

| QQ 消息类型 | 处理方式 | 候选模型／组件 |
| --- | --- | --- |
| 普通文字、Unicode Emoji | 原样保留有效文本，结合上下文生成回复 | `qwen3.8-flash` 或现有聊天模型 |
| 照片、截图、静态表情包 | 文字与图片一同输入，直接理解并生成回复 | `qwen3.8-flash`，图片能力待核验 |
| GIF 动态表情包 | 有界解码，抽取少量时序帧，与用户文字一起输入 | 图片处理组件 + 同一视觉对话模型 |
| 短语音 | 下载、识别格式、必要时解码，ASR 转写，再交给对话模型 | `qwen-audio-3.1-asr-flash`，协议待核验 |
| QQ 内置表情 | 根据事件中的 ID 映射名称，作为用户内容 | 本地映射表 + 对话模型 |
| 自动语音回复 | 对话模型先生成回复文本，再按策略调用 TTS | 现有 `qwen3-tts-flash-realtime` + SILK 编码 |

图片采用截图提出的“视觉模型直接理解并回复”，不默认先做一次图片描述、再调用一次聊天模型。一次视觉对话即可保留图片细节并减少串行调用；没有配置视觉能力时明确提示图片暂不可处理，不把图片静默丢弃。

推荐使用同一支持图片的对话模型处理文字、Emoji、图片及表情包，ASR 与 TTS 独立。也允许保留当前纯文本模型，并为带图片的消息单独配置视觉对话供应商；两条路径必须使用一致的身份信息、系统提示词和会话范围。

## 3. 总体流程

```text
QQ WebSocket / Webhook
  → 核对机器人、事件类型与发送者
  → 持久化接收记录并去重
  → 解析文字、表情、图片和语音附件
  → 限流、附件检查与有界下载
  → 图片预处理 / GIF 抽帧 / ASR 转写 / 表情 ID 映射
  → 加载机器人配置、用户身份与当前会话上下文
  → 对话模型生成一份回复文本
  → 服务端决定文字或语音回复
      ├─ 文字：QQ 被动文本回复
      └─ 语音：TTS → 必要时转 SILK → 上传媒体 → QQ 被动语音回复
  → 记录各阶段状态、耗时和最终送达结果
```

WebSocket 与 Webhook 共用同一条解析和处理链。机器人自动回复使用当前收到消息的合法回复上下文，不复用历史消息 ID，不直接调用后台主动发送入口冒充被动回复。实现前核对媒体上传、被动回复参数、序号规则及有效回复时限。

## 4. 输入处理规则

### 4.1 图片与静态表情包

- 有附带文字时，优先回答用户针对图片提出的问题。
- 只有照片或截图时，简要说明主要内容，必要时询问用户需要什么帮助。
- 只有表情包时，结合画面文字、人物动作及聊天上下文理解情绪、调侃或反讽，优先自然回应，不强制输出图片分析报告。
- 无法确定含义时使用不确定表述，不虚构图中文字或用户情绪。
- 根据真实文件头和解码结果判断格式，不仅依赖后缀或 Content-Type。
- 校正图片方向、限制像素和尺寸，转换为模型支持的格式；文字较密的截图优先保留可读性。
- 不默认增加单独 OCR 请求；视觉模型读不清时明确说明。

### 4.2 GIF 动态表情包

- 按实际 GIF 内容识别，不以“表情包”业务标签替代文件检查。
- 正确合成透明区域和局部更新帧，避免直接取原始差分帧导致画面残缺。
- 在解码预算内按播放时间均匀抽样，包含首尾有效画面，默认最多 4 帧；过滤明显重复帧。
- 将帧编号、相对时间和“同一张动态表情包的连续画面”提示一并传给模型。
- 同时限制源文件大小、帧数、累计解码像素与处理时长，防止小文件解压为超大动画。
- 超出动态处理预算时，仅在能安全解码首帧的情况下退为静态理解，并标记“仅识别首帧”；否则提示无法处理。
- QQ 若只提供不可访问的表情标识或预览图，不声称已理解完整动画。

### 4.3 语音

- 第一版每条消息最多处理 1 段、60 秒语音；按解码后的实际时长校验。
- 先确定 QQ 实际返回的编码及 ASR 支持的格式。SILK 等不受 ASR 支持的格式先解码为标准 PCM/WAV。
- 接收端 SILK 解码与现有发送端 SILK 编码分开处理，复用已有依赖，不默认引入 FFmpeg。
- 音频中提到的“忽略系统指令”等话语只是用户内容，不拥有更高权限。
- 转写为空、无人声、格式不支持或识别失败时明确报告；不伪造转写结果。
- 如果 ASR 返回置信信息，可作为提示依据；未返回时不能自行编造置信分数。
- 默认不把完整转写另外发送给 QQ 用户；后台可查看，对话模型直接据此回复，避免一段语音产生多条冗余消息。

### 4.4 Emoji、QQ 内置表情与混合消息

- Unicode Emoji 保留原字符，与普通文字共同输入模型。
- QQ 表情仅按平台确认的 ID 表映射；保留未知 ID 的占位说明，不猜测其名称或情绪。
- 图片形式的 QQ 表情仍走图片路径；无法获取图像的 ID 不伪装为图片。
- 消息同时有文字、图片、表情或语音时保留顺序和类型。ASR 结果明确标记为语音转写。
- 部分附件处理失败时，可基于成功部分回复，但要让用户知道哪些内容未识别；全部失败时返回简短错误提示，不调用对话模型编造答案。

## 5. 自动语音回复策略

每个机器人对私聊和群聊分别配置以下模式：

| 模式 | 行为 |
| --- | --- |
| 文字回复 | 所有可理解消息均回复文字，作为升级默认值 |
| 跟随语音 | 用户消息包含可成功识别的语音时回复语音，其余回复文字 |
| 优先语音 | 对文字、图片、表情包和语音的回复，符合条件时都生成语音 |

建议首次启用选择“私聊跟随语音、群聊文字回复”，管理员也可主动选择其他模式。新功能升级不自动启用付费语音回复。

规则由服务端执行，不把是否调用 TTS 完全交给模型决定：

1. 先生成回复文本，再判断回复模式、TTS 配置及输出内容。
2. `/reset`、权限错误、识别失败、限流等操作性提示一律文字回复。
3. 包含代码块、表格、长链接，或超过 300 字符的回复默认使用文字，避免难以听懂或朗读不完整。
4. 普通短回复清理不适合朗读的 Markdown 标记，保留语义；不另调模型改写。
5. TTS 默认使用 `Bunny`，允许配置官方音色 ID。保存配置不调用模型。
6. 私聊音频转为腾讯 SILK；群聊使用平台支持且已验证的 WAV 或 SILK。平台格式要求须在实现时再次核对。
7. 默认只发送一种回复形式，语音成功后不再额外发同内容文字；回复原文仍保存在聊天记录中。

失败回退：

- TTS、转码或媒体上传失败，且确定尚未发送时，在合法回复窗口内回退到原文字回复。
- QQ 明确拒绝语音发送时，只有确认允许继续回复且不会重复送达，才尝试一次文字回退。
- QQ 消息发送超时、网络中断或送达未知时，不自动补发文字，避免语音已送达后重复回复。
- 文字回退也最多尝试一次；失败记录真实结果，不能无限重试。
- 用户侧文字回退应简短说明语音暂不可用，后台记录具体失败阶段，不泄露上游原始异常或凭证。

## 6. 后台与模型配置

供应商用途与能力分开，沿用 `chat / image / asr / tts` 分类：

- `image` 保持“图片生成”，不能被当作图片理解模型。
- 图片理解供应商使用 `chat` 类型，并增加“支持图片输入”能力标记及明确的接口适配。
- 类型和能力标记只是选择约束，不代表任意 OpenAI 兼容地址实际具备该能力；连接测试及人工验收分别确认。
- ASR 和 TTS 使用各自专用协议适配，不能向它们调用 Chat Completions。

机器人新增规划配置：图片理解开关、GIF 理解开关、语音识别开关、视觉对话供应商、ASR 供应商、TTS 供应商、音色、私聊回复模式、群聊回复模式。未设置独立视觉供应商时，仅在当前聊天供应商标记支持图片且实际适配时复用。

后台提供图片试理解、短语音试转写、TTS 文本试听；必须由管理员点击触发，明确提示可能产生费用，不自动发送 QQ 消息。机器人保存配置时校验模型类型、启用状态和必填绑定，避免选择了语音回复但没有 TTS。

供应商凭证继续加密存储、查询只返回掩码。机器人配置变更仅影响对应机器人；供应商配置下次请求生效，在途请求使用已读取的配置快照。首版仅在启用后台的运行模式提供新配置，无后台模式维持既有行为。

## 7. 会话、身份与历史

- 家庭身份继续按 `bot_id + user_id` 读取，同 OpenID 的跨会话身份共享；不同 OpenID 不自动合并。
- 对话上下文继续按机器人、来源、群和用户隔离，不因为共享身份而混入其他群或私聊记录。
- 图片和转写内容始终属于用户输入，不能修改身份、角色绑定、系统规则或工具权限。
- 首版不长期保存原图、语音、GIF 帧、签名下载 URL 和 Base64 数据；下载内容只用于当前处理，临时文件及时清理。
- 当前请求可使用原始图像；后续上下文保留文字问题、语音转写和已生成的回复，不再次保存或重传完整图像。追问需要原图中的新细节时提示重新发送，不能承诺拥有长期视觉记忆。
- GIF 抽帧、ASR 和 TTS 均不改变现有按机器人隔离的接收去重规则。进程中断后不自动重放已开始发送的任务。

## 8. 建议资源限制与时限

以下为首版建议值，尚未实现。实际值以 QQ 附件和所选模型限制中更严格者为准。

| 项目 | 建议限制 |
| --- | --- |
| 图片／GIF 附件 | 每条最多 3 个，视觉输入总计最多 8 帧／图 |
| 下载体积 | 单附件最多 8 MB，每消息最多 16 MB |
| 图片解码 | 单帧最多 2000 万像素，送模型前长边最多 2048 像素 |
| GIF 解码 | 最多扫描 100 帧、累计 1 亿像素、5 秒；最多选 4 帧 |
| 语音 | 每条最多 1 段、60 秒；解码输出单独限制大小 |
| 下载 | 每附件 10 秒，总下载 20 秒 |
| ASR / 对话 / TTS | 分别最多 25 / 45 / 30 秒 |
| 本地音频转码 | 15 秒，独立进程，超时终止 |
| QQ 上传 / 发送 | 在总预算内分别限制 20 / 10 秒 |
| 单条消息全流程 | 最多 120 秒，且不得超过 QQ 合法回复窗口 |

所有阶段共享从接收时间开始的截止时间，排队耗时也计入，阶段上限不能简单累加。进入 TTS 前需要预留转码、上传、发送及一次文字回退的预算；不足时直接选择文字回复。

每条消息最多 1 次 ASR、1 次对话、1 次 TTS，首版模型自动重试关闭。下载仅对可恢复错误在总预算内最多重试 1 次。继续复用每目标／全局限流及每机器人有界队列，并给附件处理增加全局并发上限，避免多个机器人同时解码耗尽内存。

费用按实际阶段记录：文本消息通常 1 次对话；图片或 GIF 通常 1 次视觉对话；语音为 ASR + 对话；语音回复再增加 TTS。抽帧数会增加视觉输入用量，本地编解码不增加模型 API 费用。具体价格待模型确认后引用官方价格表，不把估算当作账单。

## 9. 下载与内容安全

- 附件入口只来自经现有 QQ 入口验证并归属当前机器人的事件，不接受聊天文字或模型输出指定服务器下载 URL。
- 实现时根据官方文档和脱敏样本确定允许的 QQ 媒体来源；检查 HTTPS、主机、端口、DNS 解析和目标地址，阻止回环、内网、链路本地地址及不合规重定向。
- 每次重定向重新校验，流式限制响应体积；不把机器人凭证附加给任意媒体域名。
- 文件头、解码结果、尺寸、时长分别检查。压缩包、伪造扩展名和不支持的媒体明确拒绝。
- 解码和编码放入有界后台任务或子进程，避免阻塞异步事件循环；任务取消和退出服务时释放文件、进程及网络资源。
- 日志不得记录密钥、附件签名 URL、原始媒体或完整上游错误响应。

## 10. 数据库与后台记录规划

采用新的 Alembic 手写迁移，不修改任何已经执行的迁移和快照。仅在实现阶段确定并新增迁移文件，本方案不执行迁移。

建议复用聊天记录作为一次消息处理的主记录，增加关联附件元数据表；机器人表新增能力及回复策略配置，供应商表新增图片输入能力标记。

附件记录建议包含 `bot_id`、主记录 ID、附件序号、类型、文件大小、实际格式、处理状态、错误摘要、语音转写以及抽帧数量。通过包含 `bot_id` 的约束保持归属一致，不保存二进制媒体或带签名 URL。

主记录或配套处理结果中保存识别／对话／合成供应商及模型快照、阶段耗时、上游实际返回的用量、预期回复形式、实际回复形式及回退原因。视觉模型直接生成的回复作为结果，不凭空添加一个未调用过的“图片识别摘要”。

后台区分“识别成功”“合成成功”“上传成功”“QQ 已确认发送”和“送达未知”。原有主状态继续表示最终处理结果，单独展示中间阶段；不能将 TTS 成功当作消息已送达。

## 11. 代码落点与实施步骤

优先复用现有模块，仅在职责需要时增加小模块，不引入通用插件框架或任务调度平台。

| 位置 | 规划改动 |
| --- | --- |
| `qbot/server.py` / `qbot/gateway.py` | 附件事件解析、统一入口、总时限及队列衔接 |
| `qbot/chat.py` / `qbot/recording.py` | 多模态输入、会话历史、阶段记录及回复策略 |
| `qbot/model.py` | 支持图片的对话适配，继续区分供应商用途 |
| `qbot/tts.py` / `qbot/audio_codec.py` | 复用合成和 SILK 编码，补充接收语音解码 |
| `qbot/qq.py` | 当前消息上下文中的被动媒体回复与送达判定 |
| `qbot/admin.py` / `qbot/storage.py` / `qbot/static/` | 机器人能力配置、供应商校验和结果展示 |
| 待新增小模块 | 安全附件下载、GIF 预处理、ASR 专用适配和表情 ID 映射 |

实施顺序：

1. 收集私聊／群聊的图片、语音、静态表情、GIF 和内置表情脱敏事件样本，核验候选模型及 QQ 回复协议。
2. 完成配置与手写迁移设计，接入文字／图片／静态表情的直接多模态对话。
3. 接入 GIF 抽帧与 QQ 表情 ID 映射，补齐混合消息处理。
4. 接入短语音解码、ASR、转写入库和文字回复。
5. 接入自动语音回复模式、被动媒体发送、失败回退和预算控制。
6. 完成后台阶段状态、错误信息、用量展示及部署说明，再按授权开展验收。

以上步骤全部是计划，不表示已实现；自动语音回复和表情包理解属于本次完整目标，不能在完成图片与 ASR 后将整体需求标记为完成。

## 12. 验收清单（待用户要求后执行）
